# Assumed and undocumented behavior

Every behavior here is something the implementation relies on that is not stated authoritatively
in a source the project can quote, or that is inferred. Each entry names its source. Entries marked
UNVERIFIED have not been checked against real hardware or a real title.

| ID | Behavior | Source | Status |
|----|----------|--------|--------|
| A-001 | `CNTFRQ_EL0` reads 19,200,000 Hz and `CNTPCT_EL0` ticks at that rate. | Switchbrew, SVC page, GetSystemTick: "The frequency is 19200000 Hz (constant from official sw)". The page does not say what the hardware register itself returns under Horizon, so equality with `CNTFRQ_EL0` is assumed. | UNVERIFIED |
| A-002 | RomFS image layout: a 0x50-byte header of ten little-endian u64 fields (header size, dir hash table offset/size, dir meta table offset/size, file hash table offset/size, file meta table offset/size, file data offset); directory entries are `parent, sibling, childDir, childFile, nextHash, nameLen` (six u32) followed by a UTF-8 name; file entries are `parent, sibling, dataOff (u64), dataSize (u64), nextHash, nameLen` followed by a UTF-8 name; `0xFFFFFFFF` means no entry; entries start on 4-byte boundaries. | Struct definitions in libnx `nx/include/switch/runtime/devices/romfs_dev.h` and `switch-tools` `src/romfs.c` (switchbrew, fetched 2026-10-12). The Switchbrew wiki has no reachable RomFS page. | Documented in libnx; tested only against our own builder |
| A-003 | PFS0 layout: `PFS0` magic, entry count, string table size, 4 reserved bytes, then 0x18-byte entries (offset u64 relative to the data area, size u64, string offset u32, 4 reserved), the string table, then file data. | Switchbrew, NCA page, "PFS0" section. | Documented |
| A-004 | The RomFS builder places header, hash tables and entry tables before the file data, with the data area 0x200-aligned and each file 0x10-aligned. Guest RomFS readers are assumed to follow the header offsets and not to depend on table order. | The `switch-tools` builder (`src/romfs.c`) puts file data first at 0x200 and the tables after it; both orders are reachable through the header fields (libnx reads through the header). | UNVERIFIED against a real guest reader |
| A-005 | RomFS hash tables: bucket index is `hash % bucket_count` with `hash = rotr(hash, 5) ^ byte` over the name bytes, seeded with `parent_offset ^ 123456789` (parent 0 for the root); bucket count is 3 below 3 entries, `n \| 1` below 19, otherwise the next integer not divisible by 2, 3, 5, 7, 11, 13 or 17; entries are chained by prepending. | Switchbrew `switch-tools` `src/romfs.c` (`calc_path_hash`, `romfs_get_hash_table_count`), fetched 2026-10-12. | Documented in that source; checked only against our own reader |
| A-006 | The first module is mapped at guest address `0x0800_0000` and further modules would follow it. ASLR is not emulated. | The 39-bit code region starts at `0x8000000` on the console (consistent with emulator practice and with an earlier recompiler the owner supplied); Switchbrew's Memory layout page describes ASLR but gives no fixed base. Any consistent base works for recompiled code because all addresses derive from it. | UNVERIFIED against hardware |
| A-007 | Without a `main.npdm`, a module whose first word is an A32 branch-always instruction (`0xEA......` or `0xEB......`) is treated as AArch32. With an NPDM, `Is64BitInstruction` clear or a 32-bit address space is authoritative. | Switchbrew NPDM page (Flags0, ProcessAddressSpace) for the NPDM rule. The first-word test is our own heuristic and can miss AArch32 code that starts differently. | Heuristic |
| A-008 | NSO memory layout: segments sit at their header memory offsets; everything from the end of `.data` to the page-rounded end of `.data` plus `BssSize` is zero; the segment table records page-rounded extents and a separate bss segment starting at the next page. | Switchbrew NSO0 page gives sizes and offsets but not bss placement; the MOD0 `BssStartOffset`/`BssEndOffset` fields are stored but not used to size the mapping. | Consistent with a real title (all hashes and relocations resolve) |
| A-009 | Relocation semantics: `R_AARCH64_RELATIVE` = base + addend; `ABS64`, `GLOB_DAT` and `JUMP_SLOT` = symbol address + addend when the symbol is defined in the same module. An undefined weak symbol resolves to zero; an undefined strong symbol leaves the slot zero and is reported. TLS and IRELATIVE relocations are reported and not applied. | AArch64 ELF psABI relocation definitions; Switchbrew MOD page for locating `.dynamic`. How Horizon's rtld resolves symbols across modules is not documented there, so cross-module resolution is a known gap of phase one (main only). | A real title leaves thousands of imports unresolved in phase one; see the M2 report |
| A-010 | A service name in the NPDM access list matches by glob where `*` stands for any run of characters. Entries with the server bit (bit 7) allow registering, not connecting. | Switchbrew NPDM page: "supports the wildcard `*` character" and the IsServer bit. Whether `sm` only honours a trailing `*` is not documented. | Documented, matching detail assumed |
| A-011 | A kernel-capability "enable system calls" descriptor enables SVC `index * 24 + bit` for each set bit of its 24-bit mask. A program that issues an SVC outside the enabled set is stopped by the runtime. | Switchbrew NPDM page, EnableSystemCalls (bits 5-28 mask, bits 29-31 index). The stop-the-run policy is ours. | Documented; consistent with a real title (47 SVCs enabled) |
| A-012 | Each `.eh_frame_hdr` FDE is treated as one function extent for discovery. Nested or overlapping extents (cold paths) are possible and must be reconciled by analysis. | LSB / DWARF `.eh_frame_hdr` format; MOD0 locates the header (Switchbrew MOD page). | Covered 99.9% of a real title's text |
| A-013 | `FPCR` writable bits are AHP, DN, FZ, RMode, Stride and Len (`0x07F7_0000`): the trap-enable bits are RAZ/WI and FZ16 is absent. `FPSR` writable bits are `0xF800_009F`: N, Z, C, V and QC (31:27), IDC, and the cumulative flags. | Arm register descriptions (FPSR bits 31:28 exist when AArch32 is implemented, and the Cortex-A57 implements it); the Cortex-A57 model in Unicorn agrees on every random write. | Matches Unicorn; UNVERIFIED on hardware |
| A-014 | `CTR_EL0 = 0x8444C004`; `DCZID_EL0 = 4` (`DC ZVA` clears 64 bytes). | Cortex-A57 values as reported by Unicorn's A57 model. | UNVERIFIED on a Switch |
| A-015 | No alignment check on plain loads and stores, and none on SP-based accesses. Exclusive and ordered accesses must be aligned. | Pseudocode `CheckAlignment` with `SCTLR.A = 0` for normal memory; SP alignment depends on `SCTLR_EL1.SA0`, whose value under Horizon is not known. Unicorn also does not check SP. | UNVERIFIED |
| A-016 | Local exclusive monitor: armed by `LDXR`/`LDAXR` for the exact address and size; cleared by `CLREX`, by any store-exclusive (success or failure), and by a store-exclusive to a different address or size. The PE's own plain stores do not clear it. A failing store-exclusive does no memory access; a misaligned one faults before the monitor is consulted. | Arm pseudocode (`AArch64.ExclusiveMonitorsPass`, `ClearExclusiveByAddress`). Cross-thread behavior is implemented in the runtime memory model (global monitor, spurious failure allowed). | Documented; see U-3, U-6 |
| A-017 | Choices for CONSTRAINED UNPREDICTABLE encodings: in `LDP` with `Rt == Rt2` the second register's value is kept; with writeback and `Rt == Rn` the written-back address wins over loaded data; a store-exclusive status register that overlaps a data register is written after the store. | Ours; the architecture allows any result. | Not compared against Unicorn |
| A-018 | `PAC*`, `AUT*`, `BTI`, `ESB`, `PSB`, `TSB`, `CSDB` hints execute as NOPs. | The Cortex-A57 is an Armv8.0 core without PAuth or BTI, where all unallocated hint encodings are NOPs. | Documented |
| A-019 | Not implemented and reported when executed: LSE atomics, `MSR` (immediate), `SB`, flag-manipulation (FlagM), MTE, SVE, pointer-authenticated loads and stores, and the Armv8 cryptographic extension (`AES*`, `SHA1*`, `SHA256*`; `PMULL` is implemented). None of these except the cryptographic extension exists on the Cortex-A57. | Scope decision; the decoder returns `Unsupported`, never a silent no-op. | By design |
| A-020 | The interpreter models EL0. Reads and writes of system registers outside the EL0 set (`NZCV`, `FPCR`, `FPSR`, `TPIDR_EL0`, read-only `TPIDRRO_EL0`, the counters, `CTR_EL0`, `DCZID_EL0`) and unsupported `SYS` operations stop the run with the register named. | Never inventing a value is a project rule. | By design |
| A-021 | Global exclusive monitor in the runtime: each thread has at most one reservation, for the exact address range and the bytes its load-exclusive saw. A store by another thread (plain or exclusive) that overlaps a reservation ends it; a thread's own plain stores do not, and update what its reservation saw. A store-exclusive succeeds only with its own reservation intact for exactly that range, and commits with a compare-and-exchange against what the reservation saw. A store-exclusive may fail spuriously, and the runtime can be told to make every `n`th one fail. Plain stores skip the monitor lock while no reservation exists anywhere, so a plain store that races the arming of an overlapping reservation in the same instant and writes the value already there goes unnoticed. `SVC` does not clear the reservation although an exception return does on hardware. | Arm pseudocode (`AArch64.ExclusiveMonitorsPass`, `ClearExclusiveByAddress`, `MarkExclusiveGlobal`) for the reservation rules; the exchange, the lock-skipping fast path and the granule (exact range, not the implementation-defined exclusives reservation granule) are ours. | Exercised by unit tests with two thread contexts; the residual race and the `SVC` case are UNVERIFIED |
| A-022 | Guest memory is a 39-bit address space of 4 KiB pages with R/W/X permissions. An access outside it, or to an unmapped page, is an unmapped fault; a permission failure is a permission fault. An access that straddles two pages is checked as a whole before any byte is written, and reports the access address (not the first inaccessible byte). The host bytes of unmapped pages are not freed until the process ends. | Switchbrew Memory layout page for the 39-bit process address space; the rest is ours, matching the interpreter's test memory. | Documented |
| A-023 | A memory fault, trap or unhandled supervisor call inside generated code records the faulting instruction's address, the access address, its direction and kind exactly, and ends the run; the registers of the block that was running are *not* reconstructed (the CPU structure holds the state at the last call or entry). The interpreter, including the slow path, is precise. | Ours: precise state would need every register live at every memory access. Differential tests compare the fault record, not the registers, after a fault. | By design; see the M4 report |
| A-024 | The slow path decides which `RET` returns to its native caller by counting `BL`/`BLR` (+1) and `RET` (-1) while it interprets: a `RET` at depth zero leaves, and native code entered by a branch or call returns to the interpreter. Code that unbalances calls and returns (coroutine switches, `longjmp` inside interpreted code) can leave the slow path too early or too late. | Ours. | Heuristic; every case it handles is logged with its address |
| A-025 | Barriers: `DMB LD` becomes an acquire fence, `DMB ST` a release fence, every other `DMB` and every `DSB` a sequentially consistent fence, `ISB` a compiler-only barrier. Every guest memory access is an opaque call into the runtime, so the compiler cannot reorder accesses with each other; acquire loads and release stores use acquire and release atomics inside the runtime. The x86-64 memory model, which is stronger than Arm's, covers the rest. | Arm ARM barrier definitions (`DMB` types and domains). Mapping to LLVM orderings is ours. | Checked structurally (generated text); ordering is not observable in single-threaded differential tests and no multi-threaded litmus test exists yet |
| A-026 | `FPCR` and `FPSR` are memory fields of the CPU structure, not SSA values: `MRS`/`MSR` of them are field loads and stores in program order (with the writable-bit masks of A-013), and every floating-point or SIMD instruction is a call into the runtime (`nx_vec`) that reads `FPCR` for rounding, flush-to-zero and default-NaN mode and ORs the exceptions it raises into `FPSR`. This departs from the brief's "explicit FPCR/FPSR in the IR": the flags come out of exact soft-float arithmetic inside the helper, and keeping the helper's inputs and outputs in the CPU structure avoids threading both registers through every call. The vector registers live in the CPU structure too; only the integer operand and result of an instruction (`FMOV Xd, Dn`, `SCVTF`, `DUP`, `UMOV`, ...) and the flags of `FCMP`/`FCCMP`/`FCSEL` cross the call as values. | Ours. | Differential tests cover `MRS`/`MSR` of both registers and every FP/SIMD group (lifted code against the interpreter) |
| A-027 | Jump tables are found by *running* the straight-line code in front of an indirect branch with the interpreter, for every index a preceding `cmp reg, #N` / `b.hi` (or `b.hs`) admits, reading the table from the image; the result is only a candidate set of targets. The lifter switches on the computed address and sends anything not in the set through the function table, so a wrong or missing table costs speed, never correctness. Tables whose bounds check is not in the same straight-line run, and tables indexed without a bounds check, are not found. | Ours; the compilers' idioms (LLVM `ldrsw`/`add`, GCC `ldrb`/`adr`) are public knowledge. | Tested on synthetic shapes and on a real title (367 tables found; 4,916 other indirect branches go through the function table, most of them virtual tail calls) |
| A-028 | A produced program starts like a plain process, not like a Horizon one: the module is mapped at its base, the main thread gets a 4 MiB stack ending at guest address `0x1_0000_0000`, `X0` holds the argument count, `X30` the exit address, and the program exits with the low 32 bits of `X0` when the entry function returns. Real Horizon start-up (loader configuration, handles, the SVC interface) belongs to the kernel layer in milestone M6. | Ours. | Provisional |
| A-029 | The produced library's `nx_rt_call` runs a guest function on a fresh thread context with its own stack and returns `X0`; it is the library's way to expose the module's exported symbols (`nx_rt_find_export`). It does not translate calling conventions: arguments are guest integers in `X0`..`X7`. | Ours. | Tested with a synthetic export |
| A-030 | The floating-point and Advanced SIMD instruction set is the one of an Armv8.0 Cortex-A57: no half-precision arithmetic (`FEAT_FP16`), so every half-precision form other than the `FCVT`, `FCVTN` and `FCVTL` conversions is unallocated; no `SQRDMLAH`/`SQRDMLSH` (RDM), dot product, `FCMLA`/`FCADD`, `FMLAL`, `BF16`, `FJCVTZS` or `FRINT32/64`; the cryptographic extension is present on the core but not implemented (A-019). Half-precision values in those conversions use the alternative format when `FPCR.AHP` is set. | The Cortex-A57 model in Unicorn raises UNDEFINED for every one of these encodings (millions of random words, see the M5 report); the Arm ARM defines which feature adds which encoding. | Matches Unicorn; UNVERIFIED on a Switch |
| A-031 | Floating-point exceptions never trap: the trap-enable bits of `FPCR` read as zero and ignore writes (A-013), so every exception only sets its cumulative flag in `FPSR` (`IOC`, `DZC`, `OFC`, `UFC`, `IXC`, `IDC`, and `QC` for saturating integer operations). The per-element flags of a vector instruction are ORed together. | Arm ARM `FPProcessException` and `FPSR`; a core without trap-enable bits behaves this way. | Matches Unicorn on every random case |
| A-032 | Vector loads and stores make one bus access per element or per register (a `LDR Q` is one 16-byte access, `LD4` is one access per element in structure order), so a fault part-way through a multi-register load leaves the register file unchanged but a store that faults may have written its earlier elements. Atomicity is that of the runtime's memory (two 64-bit halves for 16 bytes); the architecture only promises single-copy atomicity per element. Unaligned vector accesses are allowed, as for integer loads and stores (A-015). | Arm ARM `Mem[]` and the single-copy atomicity rules; the fault ordering is ours. | Matches Unicorn for every access that completes; partial-fault behavior is not compared |
| A-033 | The decoder is strict about should-be-zero and reserved fields in the floating-point and SIMD space (for example `FCMP Dn, #0.0` with `Rm != 0` is unallocated), and about `size`/`Q` combinations the architecture reserves (`1D` arrangements of the narrowing, permuting and element-wise integer operations). | Arm ARM encoding tables and `Reserved value` rules; Unicorn is laxer in one case (U-9). | Matches Unicorn on 8,000,000 random words apart from U-9 and U-5 |
