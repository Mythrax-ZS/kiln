# Assumed and undocumented behavior

Every behavior here is something the implementation relies on that is not stated authoritatively
in a source the project can quote, or that is inferred. Each entry names its source. Entries marked
UNVERIFIED have not been checked against real hardware or a real title.

| ID | Behavior | Source | Status |
|----|----------|--------|--------|
| A-001 | `CNTFRQ_EL0` reads 19,200,000 Hz and `CNTPCT_EL0` ticks at that rate. | Switchbrew, SVC page, GetSystemTick: "The frequency is 19200000 Hz (constant from official sw)". The page does not say what the hardware register itself returns under Horizon, so equality with `CNTFRQ_EL0` is assumed. | UNVERIFIED |
| A-002 | RomFS image layout: a 0x50-byte header of ten little-endian u64 fields (header size, dir hash table offset/size, dir meta table offset/size, file hash table offset/size, file meta table offset/size, file data offset); directory entries are `parent, sibling, childDir, childFile, nextHash, nameLen` (six u32) followed by a UTF-8 name; file entries are `parent, sibling, dataOff (u64), dataSize (u64), nextHash, nameLen` followed by a UTF-8 name; `0xFFFFFFFF` means no entry; entries start on 4-byte boundaries. | Struct definitions in libnx `nx/include/switch/runtime/devices/romfs_dev.h` and `switch-tools` `src/romfs.c` (switchbrew, fetched 2026-10-12). The Switchbrew wiki has no reachable RomFS page. | Documented in libnx; tested only against our own builder |
| A-003 | PFS0 layout: `PFS0` magic, entry count, string table size, 4 reserved bytes, then 0x18-byte entries (offset u64 relative to the data area, size u64, string offset u32, 4 reserved), the string table, then file data. | Switchbrew, NCA page, "PFS0" section. | Documented |
| A-004 | The RomFS builder places header, hash tables and entry tables before the file data, with the data area 0x200-aligned and each file 0x10-aligned. Guest RomFS readers are assumed to follow the header offsets and not to depend on table order. | The `switch-tools` builder (`src/romfs.c`) puts file data first at 0x200 and the tables after it; both orders are reachable through the header fields (libnx reads through the header). | UNVERIFIED against a real guest reader |
| A-005 | RomFS hash tables: bucket index is `hash % bucket_count` with `hash = rotr(hash, 5) ^ byte` over the name bytes, seeded with `parent_offset ^ 123456789` (parent 0 for the root); bucket count is 3 below 3 entries, `n \| 1` below 19, otherwise the next integer not divisible by 2, 3, 5, 7, 11, 13 or 17; entries are chained by prepending. | Switchbrew `switch-tools` `src/romfs.c` (`calc_path_hash`, `romfs_get_hash_table_count`), fetched 2026-10-12. | Documented in that source; checked only against our own reader |
| A-006 | The first module is mapped at guest address `0x0800_0000` and further modules follow it back to back (A-041). ASLR is not emulated. | The 39-bit code region starts at `0x8000000` on the console (consistent with emulator practice and with an earlier recompiler the owner supplied); Switchbrew's Memory layout page describes ASLR but gives no fixed base. Any consistent base works for recompiled code because all addresses derive from it. | UNVERIFIED against hardware |
| A-007 | Without a `main.npdm`, a module whose first word is an A32 branch-always instruction (`0xEA......` or `0xEB......`) is treated as AArch32. With an NPDM, `Is64BitInstruction` clear or a 32-bit address space is authoritative. | Switchbrew NPDM page (Flags0, ProcessAddressSpace) for the NPDM rule. The first-word test is our own heuristic and can miss AArch32 code that starts differently. | Heuristic |
| A-008 | NSO memory layout: segments sit at their header memory offsets; everything from the end of `.data` to the page-rounded end of `.data` plus `BssSize` is zero; the segment table records page-rounded extents and a separate bss segment starting at the next page. | Switchbrew NSO0 page gives sizes and offsets but not bss placement; the MOD0 `BssStartOffset`/`BssEndOffset` fields are stored but not used to size the mapping. | Consistent with a real title (all hashes and relocations resolve) |
| A-009 | Relocation semantics: `R_AARCH64_RELATIVE` = base + addend; `ABS64`, `GLOB_DAT` and `JUMP_SLOT` = symbol address + addend when the symbol is defined in the same module. An undefined weak symbol resolves to zero; an undefined strong symbol leaves the slot zero and is reported. TLS and IRELATIVE relocations are reported and not applied. | AArch64 ELF psABI relocation definitions; Switchbrew MOD page for locating `.dynamic`. How Horizon's rtld resolves symbols across modules is not documented there, so cross-module resolution is a known gap of phase one (main only). | A real title leaves thousands of imports unresolved in phase one; see the M2 report |
| A-010 | A service name in the NPDM access list matches by glob where `*` stands for any run of characters. Entries with the server bit (bit 7) allow registering, not connecting. | Switchbrew NPDM page: "supports the wildcard `*` character" and the IsServer bit. Whether `sm` only honours a trailing `*` is not documented. | Documented, matching detail assumed |
| A-011 | A kernel-capability "enable system calls" descriptor enables SVC `index * 24 + bit` for each set bit of its 24-bit mask. A program that issues an SVC outside the enabled set is stopped by the runtime. | Switchbrew NPDM page, EnableSystemCalls (bits 5-28 mask, bits 29-31 index). The stop-the-run policy is ours. | Documented; consistent with a real title (47 SVCs enabled) |
| A-012 | Each `.eh_frame_hdr` FDE is treated as one function extent for discovery. Nested or overlapping extents (cold paths) are possible and must be reconciled by analysis. | LSB / DWARF `.eh_frame_hdr` format; MOD0 locates the header (Switchbrew MOD page). | Covered 99.9% of a real title's text |
| A-013 | `FPCR` writable bits are AHP, DN, FZ, RMode, Stride and Len (`0x07F7_0000`): the trap-enable bits are RAZ/WI and FZ16 is absent. `FPSR` writable bits are `0xF800_009F`: N, Z, C, V and QC (31:27), IDC, and the cumulative flags. | Arm register descriptions (FPSR bits 31:28 exist when AArch32 is implemented, and the Cortex-A57 implements it); the Cortex-A57 model in Unicorn agrees on every random write. | Matches Unicorn; UNVERIFIED on hardware |
| A-014 | `CTR_EL0 = 0x8444C004`; `DCZID_EL0 = 4` (`DC ZVA` clears 64 bytes). | Cortex-A57 values as reported by Unicorn's A57 model. | UNVERIFIED on a Switch |
| A-015 | No alignment check on plain loads and stores, and none on SP-based accesses. Exclusive and ordered accesses must be aligned. | Pseudocode `CheckAlignment` with `SCTLR.A = 0` for normal memory; SP alignment depends on `SCTLR_EL1.SA0`, whose value under Horizon is not known. Unicorn also does not check SP. | UNVERIFIED |
| A-016 | Local exclusive monitor: armed by `LDXR`/`LDAXR` for the exact address and size; cleared by `CLREX`, by any store-exclusive (success or failure), and by a store-exclusive to a different address or size. The PE's own plain stores do not clear it. A failing store-exclusive does no memory access; a misaligned one faults before the monitor is consulted. | Arm pseudocode (`AArch64.ExclusiveMonitorsPass`, `ClearExclusiveByAddress`). Cross-thread behavior is implemented in the runtime memory model (global monitor, spurious failure allowed). | Documented; see U-3, U-6 |
| A-017 | Choices for CONSTRAINED UNPREDICTABLE encodings: in `LDP` with `Rt == Rt2` the second register's value is kept; with writeback and `Rt == Rn` the written-back address wins over loaded data; a store-exclusive status register that overlaps a data register is written after the store. | Ours; the architecture allows any result. | Not compared against Unicorn |
| A-018 | `PAC*`, `AUT*`, `BTI`, `ESB`, `PSB`, `TSB`, `CSDB` hints execute as NOPs. | The Cortex-A57 is an Armv8.0 core without PAuth or BTI, where all unallocated hint encodings are NOPs. | Documented |
| A-019 | Not implemented and reported when executed: LSE atomics, `MSR` (immediate), `SB`, flag-manipulation (FlagM), MTE, SVE, and pointer-authenticated loads and stores. None of these exists on the Cortex-A57. (The cryptographic extension, `AES*`, `SHA1*`, `SHA256*` and 64-bit `PMULL`, was left out until M7, which implemented it.) | Scope decision; the decoder returns `Unsupported`, never a silent no-op. | By design |
| A-020 | The interpreter models EL0. Reads and writes of system registers outside the EL0 set (`NZCV`, `FPCR`, `FPSR`, `TPIDR_EL0`, read-only `TPIDRRO_EL0`, the counters, `CTR_EL0`, `DCZID_EL0`) and unsupported `SYS` operations stop the run with the register named. | Never inventing a value is a project rule. | By design |
| A-021 | Exclusive monitor in the runtime: a thread's load-exclusive records the range it covers and the bytes it saw; its store-exclusive succeeds only for exactly that range, with the bytes still those seen, and commits with one compare-and-exchange (a 16-byte one for a pair, the host's `cmpxchg16b`). A store-exclusive may fail spuriously, and the runtime can be told to make every `n`th one fail; `CLREX`, a load-exclusive of another range, the store itself and the thread's own plain store into the range (which the architecture leaves implementation defined) end the reservation. Plain stores never consult the monitor, so a store by another thread that leaves the same bytes in place (the ABA case) is not noticed. `SVC` does not clear the reservation although an exception return does on hardware. (The design before noted every plain store of every thread under one lock while any reservation was armed anywhere, to end overlapping reservations as the architecture's global monitor does; the third title's threads sit in load-exclusive loops all the time, so nearly every store took that lock: in its opening cutscene the main thread spent about half its samples waiting for it, `tools/sample_threads.ps1`.) | Arm pseudocode (`AArch64.ExclusiveMonitorsPass`, `ClearExclusiveByAddress`) for the reservation rules; the compare-and-exchange in place of a global monitor is how Ryujinx and yuzu implement store-exclusive (read as documentation); the granule (the exact range, not the implementation-defined exclusives reservation granule) is ours. | Exercised by unit tests with two thread contexts, the ABA case among them |
| A-022 | Guest memory is a 39-bit address space of 4 KiB pages with R/W/X permissions. An access outside it, or to an unmapped page, is an unmapped fault; a permission failure is a permission fault. An access that straddles two pages is checked as a whole before any byte is written, and reports the access address (not the first inaccessible byte). The host bytes of unmapped pages are not freed until the process ends. | Switchbrew Memory layout page for the 39-bit process address space; the rest is ours, matching the interpreter's test memory. | Documented |
| A-023 | A memory fault, trap or unhandled supervisor call inside generated code records the faulting instruction's address, the access address, its direction and kind exactly, and ends the run; the registers of the block that was running are *not* reconstructed (the CPU structure holds the state at the last call or entry). The interpreter, including the slow path, is precise. | Ours: precise state would need every register live at every memory access. Differential tests compare the fault record, not the registers, after a fault. | By design; see the M4 report |
| A-024 | The slow path decides which `RET` returns to its native caller by counting `BL`/`BLR` (+1) and `RET` (-1) while it interprets: a `RET` at depth zero leaves, and native code entered by a branch or call returns to the interpreter. Code that unbalances calls and returns (coroutine switches, `longjmp` inside interpreted code) can leave the slow path too early or too late. | Ours. | Heuristic; every case it handles is logged with its address |
| A-025 | Barriers: `DMB LD` becomes an acquire fence, `DMB ST` a release fence, every other `DMB` and every `DSB` a sequentially consistent fence, `ISB` a compiler-only barrier. Every guest memory access is an opaque call into the runtime, so the compiler cannot reorder accesses with each other; acquire loads and release stores use acquire and release atomics inside the runtime. The x86-64 memory model, which is stronger than Arm's, covers the rest. | Arm ARM barrier definitions (`DMB` types and domains). Mapping to LLVM orderings is ours. | Checked structurally (generated text); ordering is not observable in single-threaded differential tests and no multi-threaded litmus test exists yet |
| A-026 | `FPCR` and `FPSR` are memory fields of the CPU structure, not SSA values: `MRS`/`MSR` of them are field loads and stores in program order (with the writable-bit masks of A-013), and every floating-point or SIMD instruction is a call into the runtime (`nx_vec`) that reads `FPCR` for rounding, flush-to-zero and default-NaN mode and ORs the exceptions it raises into `FPSR`. This departs from the brief's "explicit FPCR/FPSR in the IR": the flags come out of exact soft-float arithmetic inside the helper, and keeping the helper's inputs and outputs in the CPU structure avoids threading both registers through every call. The vector registers live in the CPU structure too; only the integer operand and result of an instruction (`FMOV Xd, Dn`, `SCVTF`, `DUP`, `UMOV`, ...) and the flags of `FCMP`/`FCCMP`/`FCSEL` cross the call as values. | Ours. | Differential tests cover `MRS`/`MSR` of both registers and every FP/SIMD group (lifted code against the interpreter) |
| A-027 | Jump tables are found by *running* the straight-line code in front of an indirect branch with the interpreter, for every index a preceding `cmp reg, #N` / `b.hi` (or `b.hs`) admits, reading the table from the image; the result is only a candidate set of targets. The lifter switches on the computed address and sends anything not in the set through the function table, so a wrong or missing table costs speed, never correctness. A compiler that switches inside a loop computes the table's address once, before the loop, into a callee-saved register; the run starts with every register from x19 to x28 that the function's decoded code gives one constant value (`adr`, `adrp` with or without the `add`, `movz`, and nothing else writing it, restores from the stack not counted). Tables whose bounds check is not in the same straight-line run, and tables indexed without a bounds check, are not found. | Ours; the compilers' idioms (LLVM `ldrsw`/`add`, GCC `ldrb`/`adr`) are public knowledge. | Tested on synthetic shapes and on a real title (367 tables found; 4,916 other indirect branches go through the function table, most of them virtual tail calls); the constant registers resolved a switch inside a loop that a census had found among the hottest interpreted code of a cutscene |
| A-028 | A module the runtime is told to start as a plain function (hosts, tests; module kind 0) starts like a plain process, not like a Horizon one (an NSO or NRO built by `kiln build` now runs on the kernel layer, A-034 to A-040): the module is mapped at its base, the main thread gets a 4 MiB stack ending at guest address `0x1_0000_0000`, `X0` holds the argument count, `X30` the exit address, and the program exits with the low 32 bits of `X0` when the entry function returns. Real Horizon start-up (loader configuration, handles, the SVC interface) belongs to the kernel layer in milestone M6. | Ours. | Provisional |
| A-029 | The produced library's `nx_rt_call` runs a guest function on a fresh thread context with its own stack and returns `X0`; it is the library's way to expose the module's exported symbols (`nx_rt_find_export`). It does not translate calling conventions: arguments are guest integers in `X0`..`X7`. | Ours. | Tested with a synthetic export |
| A-030 | The floating-point and Advanced SIMD instruction set is the one of an Armv8.0 Cortex-A57: no half-precision arithmetic (`FEAT_FP16`), so every half-precision form other than the `FCVT`, `FCVTN` and `FCVTL` conversions is unallocated; no `SQRDMLAH`/`SQRDMLSH` (RDM), dot product, `FCMLA`/`FCADD`, `FMLAL`, `BF16`, `FJCVTZS` or `FRINT32/64`; the cryptographic extension (AES, SHA-1, SHA-256, 64-bit `PMULL`) is present on the core and implemented (M7). Half-precision values in those conversions use the alternative format when `FPCR.AHP` is set. | The Cortex-A57 model in Unicorn raises UNDEFINED for every one of these encodings (millions of random words, see the M5 report); the Arm ARM defines which feature adds which encoding. | Matches Unicorn; UNVERIFIED on a Switch |
| A-031 | Floating-point exceptions never trap: the trap-enable bits of `FPCR` read as zero and ignore writes (A-013), so every exception only sets its cumulative flag in `FPSR` (`IOC`, `DZC`, `OFC`, `UFC`, `IXC`, `IDC`, and `QC` for saturating integer operations). The per-element flags of a vector instruction are ORed together. | Arm ARM `FPProcessException` and `FPSR`; a core without trap-enable bits behaves this way. | Matches Unicorn on every random case |
| A-032 | Vector loads and stores make one bus access per element or per register (a `LDR Q` is one 16-byte access, `LD4` is one access per element in structure order), so a fault part-way through a multi-register load leaves the register file unchanged but a store that faults may have written its earlier elements. Atomicity is that of the runtime's memory (two 64-bit halves for 16 bytes); the architecture only promises single-copy atomicity per element. Unaligned vector accesses are allowed, as for integer loads and stores (A-015). | Arm ARM `Mem[]` and the single-copy atomicity rules; the fault ordering is ours. | Matches Unicorn for every access that completes; partial-fault behavior is not compared |
| A-033 | The decoder is strict about should-be-zero and reserved fields in the floating-point and SIMD space (for example `FCMP Dn, #0.0` with `Rm != 0` is unallocated), and about `size`/`Q` combinations the architecture reserves (`1D` arrangements of the narrowing, permuting and element-wise integer operations). | Arm ARM encoding tables and `Reserved value` rules; Unicorn is laxer in one case (U-9). | Matches Unicorn on 8,000,000 random words apart from U-9 and U-5 |
| A-034 | The process memory map: modules from `0x0800_0000` (A-006); the alias region at `0x20_0000_0000` (64 GiB), the heap region at `0x30_0000_0000` (6 GiB; `SetHeapSize` always returns its start), the stack region at `0x38_0000_0000` (2 GiB; `MapMemory` may map only there), thread-local regions from `0x3C_0000_0000` (8 slots of `0x200` bytes to a page, the first slot of each page unused), the homebrew loader configuration at `0x2F_0000_0000`, the main thread's stack ending 1 MiB below the end of the stack region (8 MiB for an NRO; for an NSO the NPDM's main-thread stack size rounded up to a page, 1 MiB when there is none). `GetInfo` reports these regions. `QueryMemory` reports the memory types and attributes of Switchbrew's table and merges neighbours that are equal. | Ours: Switchbrew's SVC pages define the `GetInfo` region queries, the memory types, the `MemoryInfo` layout and the attribute bits, not the addresses, which the real kernel randomizes. | UNVERIFIED against hardware; nothing here is randomized |
| A-035 | `sm:` answers `RegisterClient` (command 0, needs the process id in the message) and `GetServiceHandle` (command 1) with Atmosphère's result values: invalid client (no `RegisterClient` yet) `0x415`, invalid name `0xC15`, not allowed `0x1015` (not registered, `0xE15`, is defined but never answered: see the stop rule below). `GetServiceHandle` checks in that order: registered client, name valid, NPDM access list. A program without an NPDM (a homebrew NRO) may use every implemented service. A name the program may use that nothing implements is not answered with an error: the run stops and names the service. `RegisterService` and `UnregisterService` are not implemented. | The command ids are Switchbrew's (pre-12.0.0). The result values (module 21, descriptions 2, 6, 7 and 8) were checked against Atmosphère's `sm_results.hpp`; the order of the checks is from memory of its `sm` and not confirmed. The stop rule is the project's. | Values checked against Atmosphère's source; behavior UNVERIFIED against a console |
| A-036 | Values the kernel reports that nothing in the sources fixes: the loader configuration claims firmware 12.1.0 (`HosVersion`); `GetInfo` `TotalMemorySize` and `TotalNonSystemMemorySize` are `0xCD500000`, the application pool of a 4 GiB console (3285 MB in Atmosphère's `KSystemControl::GetApplicationPoolSize`, which I read for this) (a title sets a heap of about 3.1 GiB, which must fit; the pages are only committed when touched); `IdleTickCount` is 0 (idle time is not measured); the process id is `0x80`; `IsApplication` is 1 for an NSO and 0 for an NRO; without an NPDM the core mask is `0x7` and the priority mask all ones; `SystemResourceSizeTotal` comes from the NPDM (0 without one) and `SystemResourceSizeUsed` is 0; `GetInfo` types `ResourceLimit` (9), `UserExceptionContextAddress` (20), `FreeThreadCount` (24), `ThreadTickCount` (25) and 26 to 28 stop the run when asked, while 19 and every type above 28 answer with an invalid-enum-value result. | Ours; chosen to be plausible and documented here. | Provisional |
| A-037 | Guest threads are host threads that run truly in parallel. Priorities, ideal cores and core masks are stored and returned but do not schedule anything: there is no time slicing, no priority preemption and no core affinity. A guest that relies on priority and affinity for mutual exclusion (two threads on one core, the higher priority running until it blocks) can behave differently. `SynchronizePreemptionState` does nothing because nothing is preempted; `GetCurrentProcessorNumber` returns the thread's ideal core (0 when none was given); `SleepThread` with 0, -1 or -2 only yields the host thread. | Ours. | By design; no multi-core scheduling model exists |
| A-038 | The user-mode mutex and condition variable follow Atmosphère's kernel (`kern_k_condition_variable.cpp`, which I read for this): a mutex word holds the owner's thread handle, with bit 30 set when waiters exist; `ArbitrateLock` waits only while the word is still `owner \| bit 30` (and refuses an owner handle that is not a thread of the process); `ArbitrateUnlock` hands the lock to the highest-priority (then oldest) waiter, writing its handle and keeping bit 30 if more wait, or zero when none do; `WaitProcessWideKeyAtomic` sets the key word to 1, then releases the mutex (in that order, A-173), waits and returns holding the mutex, while a timeout returns `0xEA01` without it; `SignalProcessWideKey` sets the key word to 0 once nobody waits on it; a signalled waiter takes a free mutex at once and otherwise queues behind the owner. The order among equal waiters (priority, then arrival) is ours: the file does not show the comparator. `WaitForAddress`/`SignalToAddress` implement the three wait types and the first two signal types; `SignalAndModifyBasedOnWaitingThreadCountIfEqual` stops the run. Only libnx's own use of these calls was read, nothing was checked on hardware. | The SVC register layouts and the arbitration enums are Switchbrew's (its SVC page describes no behavior); the word protocol is Atmosphère's source. | Checked against Atmosphère's source, not a console; exercised by unit tests with real threads and by a native program (two threads, 2000 exclusive increments) |
| A-039 | `OutputDebugString` writes the bytes unchanged to standard output (the produced program's own, not standard error), without adding a newline or a prefix. `Break` with bit 31 of the reason set (notification only) returns success; any other `Break` stops the run with the reason named. `ExitProcess` ends the program with status 0, a returning entry function with `X0`, the last thread ending with 0 and any stop with 101. | The register layouts are Switchbrew's; where output goes and the exit statuses are ours. | By design |
| A-040 | IPC details beyond the HIPC/CMIF layouts Switchbrew documents: the reply's raw word count includes the alignment padding in front of the raw data; `QueryPointerBufferSize` (control command 3) answers 0, so clients are expected to send no pointer descriptors; a close message (type 2) is answered with success; `CloneCurrentObject` and `CloneCurrentObjectEx` (2, 4) return a second handle to the same session; `ConvertCurrentObjectToDomain` (0) makes the session's root object id 1 and later objects ids from 2, and a domain "release" call forgets the object; control command 1 (`CopyFromCurrentDomain`), every control command above 4 and every message type other than request, control and close stop the run; the receive list (C descriptors) of a request is not parsed, so a service never sees one; a reply that does not fit the 0x100-byte message buffer makes `SendSyncRequest` return `0xCE01`. | Switchbrew "IPC Marshalling" for the layouts; the rest is ours. | Unit-tested on bytes and through native code |
| A-041 | A title's NSOs are mapped back to back in the order `rtld`, `main`, `subsdk0` to `subsdk9`, `sdk`, each starting where the page-aligned end of the one before (its text, rodata, data and bss) ends, the first at `0x0800_0000` (A-006); the process starts in `rtld`. The image a produced program starts from is what the files hold, *not relocated*: the title's own `rtld` finds its modules with `QueryMemory` and relocates them. The analysis uses relocated copies (to read jump tables and pointers) but never embeds them (`BuildOptions::pre_relocated` is for tests that call functions directly). | Order: Switchbrew (ExeFS, Memory layout). Contiguity and the start in `rtld`: how the kernel's loader maps a program, as I remember it; a real title's `rtld` completing the linking of all its modules against this layout is the evidence. | Held on the one title tried (its `rtld` found the modules and the SDK started); other titles untested |
| A-042 | `apm`: the console is in handheld performance mode (`GetPerformanceMode` returns 0), `IsCpuOverclockEnabled` is false, a session remembers the configuration set for each mode, and a new session reports `0x00020003` for the normal mode (the value Switchbrew gives as the default of `GetCurrentPerformanceConfiguration` of `apm:sys`; it does not say what a new session reports, and the title asks before it sets anything). | A-043 | The applet manager (`appletOE`): the program is the only applet, always in focus (`GetCurrentFocusState` 1), the console is handheld (`GetOperationMode` 0, `GetPerformanceMode` 0) with a 1280x720 default display, and the first `OpenApplicationProxy` queues one `FocusStateChanged` message (15), after which `ReceiveMessage` answers `0x680` (no message). `PopLaunchParameter` answers 2128-0002 (`0x480`, "IStorage not available"); reading or writing a storage outside its size answers 2128-0503 ("IStorage read/write out of bounds"); the applet resource user id is 1; `NotifyRunning` answers true; `GetPseudoDeviceId` answers a fixed 16 bytes; `IsGamePlayRecordingSupported` is false and `InitializeGamePlayRecording` accepts the 0x6000000-byte transfer memory it is documented to take and records nothing; the event `GetLibraryAppletLaunchableEvent` hands out is set every time it is asked for (the title waits for it at start-up; library applets can be launched), but `CreateLibraryApplet` stops the run and names the applet id and mode, because library applets are firmware; the other events handed out (GPU error, health warning, display resolution change) never signal. | A-281 | The instances of a series of draws (`BEGIN` with the next instance, or an `_INSTANCE_SUBSEQUENT` draw) that draw the same vertices or indices with the same primitive, one right after the other, with no write between them that changes a register or does anything else (a constant buffer load, a semaphore, a macro load, a clear, another engine or the channel), are one draw of that many instances. The 3D engine holds each draw until a write that is not of that kind, until another engine or the channel is written to, or until the end of the GPFIFO entry, and only then gives it to the renderer; a draw the renderer refuses is reported then. The renderer draws them as one draw (the program sees each instance's number as the counter of the first plus its index), with each instanced stream bound at the rate of instances from the element of the first; a task and mesh draw, or one with a stream that gives an element to several instances (a divisor above 1), is drawn an instance at a time as before. | Ours: the hardware runs the instances as a series of draws, which the title's macros make one by one; nothing the renderer reads can change between them unless a write changes it. The title's race draws some 1,900 of its 4,600 draws a frame as later instances of a series. | Design |
| A-282 | Within a frame, what a texture was bound with (its view, sampler and layout) is kept by its header, its sampler and the way it is sampled, with the guest memory it is made of and the render targets over that memory (when each was last drawn to and whether its pixels are in memory), when binding it copied nothing and wrote nothing back and it is not a target's own view. A later draw of the frame with the same header, sampler and way of sampling takes it while each of those targets is as it was, unless the renderer wrote into that memory or placed a target over it since. A texture that is a render target's own picture is kept the same way, and taken again while the target is as it was, in the layout for sampling, and not one the draw writes or tests against. | Ours: a texture is compared with memory once a frame anyway (A-126), the copies of targets into it are judged by when each was drawn to (A-113), and nothing else decides what binding it gets. The title's race binds some 16,000 textures a frame, two thirds of them again. | Design |
